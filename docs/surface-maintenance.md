# 长会话表面对账

记忆组装默认读取现有 checkpoint。自动衰减对账改在回合结束后做；用户明确提层和当前请求需要的容量修复仍及时执行。

用户手动选择优先于自动单块预算；已生效的手动选择不会被容量修复立即降回低层。整体窗口检查、具体等待或失败说明和相邻用户操作的保护规则见[用户操作优先级](user-operation-priority.md)。

## 写入规则

- 一轮对账收集每个 Block 的最终层级，再调用一次 `setBlockSurfaceLevels()`。
- 相同层级不写库，不生成快照，也不更新 revision。检查在写队列内完成，避免并发的相同请求重复提交。
- 单条 `setBlockSurfaceLevel()` 保留，内部使用批量接口。
- 数据库层级更新具有事务性。原生会话日志与记忆库分别保存；中途失败时，按实际 checkpoint 重算和重试，不能视作跨库事务。

## 后台什么时候跑

封块、派生完成、衰减设置变化、宿主压缩或容量变化后，给会话标记待处理。同一会话的任务会合并。

新回合开始时暂停未执行的维护。组装正在等待检索时也不启动维护。任务等相关入库完成后，基于最新状态计算并连续应用 checkpoint，再统一记账。计算和应用之间没有异步等待，避免旧文本在后来的用户提层之后生效。

`flush()` 只等待入库，不等待自动表面维护。失败后保留待处理状态并退避重试；关闭时取消定时器，等待已开始的任务结束。重启后会检查现有 checkpoint，也会尝试补回保存 Block 后丢失的封块请求；宿主已压缩掉的原始范围不会被重新插入。

自动恢复只处理原片段仍在当前上下文中的 Block。宿主压缩后失效的自动任务会移出队列，后续对账不再为这些历史 Block 渲染内容；每轮共用一次来源筛查。用户明确选择仍保留同步失败原因，保存失败且来源仍在的任务继续重试。

## 怎么验证

相关测试：`packages/core/tests/surface-levels.test.ts`、`tests/surface-maintenance.test.ts`、`tests/issue81-surface.test.ts`。

用符合项目要求的 Node 版本执行：

```powershell
node scripts/benchmark-surface-assembly.mjs --base=<修复前的提交> --rounds=12
```

脚本只使用临时目录里的构造数据和 SQLite，不打开用户数据库。基线 runtime/store 从指定 Git 提交读取，其余依赖共用当前版本。结果、逐轮样本、源码哈希及两个版本的构建文件保存在 `.benchmarks/surface-*/`。

测试区分首次需要衰减的组装、维护后的稳定组装、后台对账，以及重复调用同值 setter。没有接入真实向量服务，因此耗时不能代替真实长会话的端到端测量。事件循环延迟使用 1ms 分辨率的 `monitorEventLoopDelay`，包括调度延迟。
