## 根因与修复

原 Worker 在上一轮结束后重新安排 3 秒轮询，问题不是计时器重叠，而是每轮完整打开所有 namespace 才判断有无任务，以及 SQLite 打开时重复检查各 namespace 的 FTS 完整性。持久化派生索引已消除这一发现路径。本轮进一步修复独立复审发现的三个问题：

1. **未变化的历史消息被重新标记为 FTS dirty。** 快照 UPSERT 会触发 UPDATE，但原触发器不检查变化。现在 UPSERT 跳过完全未变化的消息；FTS 触发器只关注内容、Block 归属、namespace 或 ID 的实际变化。直接 SQL 修改仍会标记旧键和新键，惰性修复保持增量。触发器升级置于事务内，避免安装期间漏掉并发写入。
2. **前八个损坏键饿死后续健康键。** 重建新增持久化 `rebuild_after`，失败键等待 60 秒；通过到期索引选择下一批，跨重启继续。源数据变化立即重置等待并更换 generation。脏键不会使用过时的调度条目，失败也不会要求零延迟重排。该字段只属于可重建索引的修复信息，没有替代 Job 重试状态。
3. **只有可封存 open tail 时反复加载而不封存。** Worker 使用 Core 的 `hasSealableTail()`，与实际封存使用同一判定；重启后即使没有任何 Job 也能生成 Block，完成后不再重复打开。直接 SQL 移除或移动 open tail 时也会使旧 namespace 失效。

全范围自查及兼容复验另外发现并修复：

- **额度恢复的毫秒竞态：** 本轮发现时间和历史额度截止时间原先各读一次时钟，跨毫秒时可能把可用额度当作未来到期；现在共享同一个 `now`，回归刻意让每次时钟读取递增。
- **长模型超过租约时重复调用：** Summary、Extraction、Graph、Topic 仅在模型执行期间定期续租。续租只更新持久化 Job 元数据，不加载历史记忆，不修改业务 revision。正常保存会合并同一 running attempt 的新租约；恢复或完成写入在同一事务内校验修改前的租约，防止旧快照缩短租约或覆盖新认领。Topic 完成后仍清除租约，既有状态语义保留。租约停止续期后，原有到期恢复和尝试上限继续生效。
- **空认领产生 revision 写入：** Graph/Topic 无可认领工作时直接返回，避免另一 worker 为一个空认领保存快照并使模型所有者的结果失效。
- **Windows 测试进程压力：** 本地复验捕获了子进程启动 `EBUSY` 及其引起的 Vitest 进程池错误，不能把该轮断言通过当作整体通过。Windows CI 现在最多启动两个测试 worker；单项超时不变。后续在本任务内独立 Node 24/npm 入口下完整复验通过，未更改系统 Node 或其他任务运行时。

## 空闲路径与旧任务

空闲轮询只检查持久化调度/脏键到期索引、模型是否就绪、历史额度和独立 Profile Maintenance。不会枚举全部 namespace、打开完整记忆、读取原始消息正文、遍历历史 Graph 或重新计算全部 Topic 资格，也不再做全库 FTS 完整性检查。

Jobs、Event 及 Topic ledger 始终是事实来源。任务保存与派生索引更新在同一事务中完成；同进程通知只是唤醒提示。跨进程写入由 SQLite 触发器留下持久化脏键，原有 3 秒轻量轮询发现它们。升级只初始化键列表，重建按 namespace 和 Event 批次让出事件循环，发布前校验 generation；重启、失败退避或模型未就绪不会丢掉待重建键。Topic 的 Event 版本变化即使尚无 Job，也参与派生资格计算。历史额度到期后恢复，Profile Maintenance 独立运行。
